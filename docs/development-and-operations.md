# 말랑콩떡 · 개발·운영 노트

개발 환경 실행, 실제 매장 연결, 배포와 운영 구조를 정리한 문서입니다. 서비스의 대상 사용자·업무·구현 현황은 [README](../README.md)에서 확인할 수 있습니다.

매장명·토끼 로고·크림/갈색 테마를 적용했습니다. 인스타그램 바로가기는 유지하며 게시물 사진은 삭제했습니다. 사용자가 첨부한 메뉴판에서 설기류 15종·오븐떡 5종·일반떡 16종의 이름, 가격, 포장 수량과 개별 사진 영역을 등록했습니다. 설기류·오븐떡은 박스당 24개이며, 일반떡은 메뉴판의 24개·25개 표기를 따르고 개수 미표기 8종은 사용자 지시에 따라 1세트 30개로 등록했습니다. 원본과 표시 방식은 `public/menu/SOURCE.md`, 구조화된 메뉴는 `src/lib/menu-catalog.ts`에 있습니다. 메뉴판의 포장 수량과 별개로 기존 레시피·생산 수율은 유지합니다.

아이폰·안드로이드·PC에서 사용하는 떡집 주문·생산·재고 관리 PWA입니다.

## 바로 실행

Node.js 22 이상을 사용합니다.

```powershell
npm ci
npm run dev
```

표시되는 로컬 주소를 엽니다. Supabase 설정이 없으면 **체험 모드**로 실행됩니다. 예시 주문·레시피는 가상 데이터이며 변경사항은 해당 브라우저에만 저장됩니다. 체험 모드는 실제 사용자 인증이나 기기 간 공유, AI 호출을 흉내내지 않습니다.

## 실제 매장 연결

1. Supabase 프로젝트를 준비하고 SQL Editor에서 `supabase/migrations/202611050001_store.sql`을 실행합니다. 이미 적용한 마이그레이션은 재실행하지 않습니다.
2. `.env.example`을 `.env.local`로 복사하고 Supabase URL, publishable/anon key, **서버 전용 service_role key**를 입력합니다. 키를 소스에 저장하거나 채팅으로 보내지 않습니다.
3. Supabase Authentication에서 공개 회원가입을 끄고, 이메일 로그인과 자체 SMTP를 설정합니다. Site URL과 Redirect URLs에 실제 앱의 HTTPS 주소를 등록합니다. 로컬 확인 시 `http://localhost:3000`도 허용합니다.
4. `APP_URL`을 실제 앱 주소로 설정하고 두 사용자를 연결합니다. 아래는 예시 이메일이므로 실제 주소로 바꿉니다. 이 명령은 계정 초대 메일을 보내며 기존 주문·재고를 초기화하지 않습니다.

```powershell
node --env-file=.env.local scripts/bootstrap.mjs owner@example.com partner@example.com
```

5. 두 사용자가 이메일 초대 링크로 접속한 뒤 **매장 설정 → 비밀번호 설정·변경**에서 직접 비밀번호를 설정합니다. 이후 이메일·비밀번호로 로그인합니다.
6. **재료·비품 → 초기 재고 등록 → 매장 설정의 메뉴·레시피 → 추천 기준** 순으로 실제 데이터를 등록합니다. 메뉴판의 설기류·오븐떡·일반떡 36종은 자동 등록하며, 가상 주문·재고는 운영 데이터에 삽입하지 않습니다. 새 메뉴의 레시피와 생산 수율은 미등록 상태입니다.

공개 회원가입을 껐더라도 `shop_members`에 등록되지 않은 계정은 데이터와 이미지에 접근할 수 없습니다. DB는 매장당 두 사용자만 허용합니다. 사용자 교체는 Supabase 관리자 화면에서 기존 멤버십을 제거한 뒤 진행합니다.

## AI 연결

서버 환경에 `OPENAI_API_KEY`, 선택적으로 `OPENAI_MODEL`을 설정합니다. 기본 모델 설정은 `gpt-4.1-mini`이며 도구 호출과 구조화 출력을 지원하는 모델로 변경할 수 있습니다. 연결 키가 없거나 호출에 실패해도 직접 생산계획 작성은 가능합니다.

생산 추천 AI는 고객명·연락처·스티커 문구를 받지 않습니다. 떡별 예약 합계, 메뉴·레시피, 재고와 생산 이력만 조회하고 시뮬레이션 도구로 추천을 검증합니다. 최종 추천도 서버에서 한 번 더 검증하며 저장·생산 완료 권한은 없습니다. 추천 API는 매장 로그인과 멤버십이 필요합니다.

### 음성 주문 입력

주문 등록·수정 화면의 **말로 입력 → 말하기 → 입력 마침**으로 주문 초안을 채웁니다. 한국어 음성에서 고객명·연락처·수령 일시·픽업/퀵/배달·주소·메뉴와 개/박스 수량·선물세트 상자당 구성·스티커 문구를 추출합니다. 말하지 않은 값은 기존 입력을 유지하고, 불확실한 메뉴나 내용은 확인 사항으로 표시합니다. 초안을 확인하고 기존 주문 등록·수정 버튼을 눌러야 저장됩니다.

서버의 `OPENAI_API_KEY`와 선택적으로 `OPENAI_REALTIME_MODEL`을 설정합니다. 기본 모델은 `gpt-realtime-2.1`입니다. 브라우저는 WebRTC로 마이크 음성을 전송하고, 서버가 `/v1/realtime/calls`에 연결해 SDP만 반환하므로 비밀키는 브라우저에 노출되지 않습니다. 참고: [OpenAI WebRTC 문서](https://developers.openai.com/api/docs/guides/voice-webrtc).

음성 입력을 시작하면 **현재 주문 양식의 내용·메뉴 이름과 포장 수량·마이크 음성**이 OpenAI로 전송됩니다. 다른 주문 목록·재고는 보내지 않습니다. 인식 문구는 입력 화면에만 표시하며 원음과 전사문을 매장 DB에 저장하지 않습니다. 최대 2분 후 자동으로 입력을 마치며, 완료·취소·오류·양식 닫기 시 마이크와 연결을 해제합니다.

현재처럼 공유 설정 없이 브라우저에 주문을 저장하는 앱은 배포 후에도 로그인 없이 음성 입력을 사용할 수 있으며, 현재 브라우저의 메뉴판을 사용합니다. Supabase 공유 모드를 연결하면 기존 매장 로그인·멤버십 확인과 서버 메뉴판을 사용합니다. 두 모드 모두 같은 출처의 요청만 받고, 서버 인스턴스별로 사용자당 분당 6회·전체 분당 30회까지 연결을 허용합니다. 이 제한은 인스턴스 메모리를 사용하므로 여러 인스턴스를 합산하는 영구적인 사용 한도는 아닙니다. HTTPS 또는 localhost와 브라우저 마이크 권한이 필요합니다.

실기기 확인 예시:

- “테스트고객, 내일 오전 열 시 픽업. 백설기 두 박스, 꿀떡 다섯 개.” → 한국 시간 기준 다음 날, 10:00, 박스 2와 개 5가 구분되는지 확인
- “선물세트 세 상자, 상자마다 백설기 두 개 꿀떡 한 개. 스티커는 생신 축하드립니다.” → 전체 3상자와 상자당 2개·1개가 구분되는지 확인
- “내일 오후 두 시 반 퀵. 주소는 아직 못 받았어.” → 14:30과 퀵이 선택되고 주소가 지어내지지 않는지 확인
- 입력 마침·취소·양식 닫기·마이크 거부·연결 실패 후 휴대폰 마이크 표시가 해제되고, 등록을 누르기 전 주문 건수가 늘지 않는지 확인

## 업무 흐름

- **예약장:** 개·박스 주문과 상자마다 직접 구성하는 선물세트를 등록합니다. 수령 일시·고객 정보·채널·스티커 문구와 참고 이미지(PNG/JPG/WebP, 최대 5MB)를 보관합니다. 체험 모드 이미지는 최대 1MB입니다.
- **생산:** 레시피의 한 생산 단위 완성량으로 날짜별 올림합니다. 예약 생산 여분과 유효한 완제품을 진열 목표에 포함합니다. 계획 확정 후 실제 완성량과 실제 재료 사용량을 입력하면 생산·재료 차감을 함께 저장합니다. 부족하면 완료되지 않으며 입고·실사 보정 후 계획을 다시 확정해야 합니다.
- **재고 예측:** 기본 7일의 예약 필요량과 진열·추가 계획 예상량, 부족량·첫 부족일을 조회합니다. 미래 진열 목표도 매일 적용한 **예상치**이며 판매량 예측은 아닙니다. 여러 날 품목은 아직 팔리지 않은 것으로 가정한 가용 여분을 이월하므로 실제 판매 후 마감 기록으로 갱신해야 합니다. 기준 미등록 메뉴는 계산할 수 없다고 표시합니다.
- **수령:** 재료를 추가 차감하지 않습니다. 등록된 완제품은 판매 기한이 빠른 생산분부터 차감하며 수령 전 상태로 되돌리면 복구합니다. 이미 마감 수량에 반영된 수령은 기록을 소급 변경하지 않고 실사 내역으로 보정합니다. 생산 기록이 아직 없어도 수령 표시 자체는 가능합니다.
- **마감:** 생산일별 잔량·폐기·기타 출고를 기록합니다. 차액은 예약 수령을 포함한 판매 추정량이며 POS 매출이 아닙니다. 당일 판매 잔량은 다음 날 가용 재고에서 제외되지만 폐기 기록은 직접 남깁니다. 판매 가능 기간은 매장에서 정한 값이며 법정 유통기한을 산정하지 않습니다.
- **비품:** 개·g·ml의 기본 단위로 직접 입출고하고 부족 기준을 설정합니다. 주문 구성으로 포장재를 자동 차감하거나 발주하지 않습니다.
- **공유:** 다른 기기의 변경은 포커스 복귀 시 및 20초 간격으로 조회합니다. 입력 양식이 열려 있으면 자동 갱신을 멈춥니다. 저장 충돌 시 내용을 유지하며, 양식을 닫고 새로고침한 후 다시 확인합니다.

메뉴별 박스 환산과 주문별 선물 구성을 저장 시 보관합니다. 레시피 변경은 완료된 생산의 당시 기준을 바꾸지 않습니다. 운영 시간은 한국 시간이며 온라인 사용이 필요합니다. 연결 실패 시 화면의 입력은 유지하되 서버 저장 성공 전에는 완료로 표시하지 않습니다.

## 저장·보안 구조

`shop_state.document`는 주문·메뉴·생산·입출고·마감 기록을 포함하는 버전 관리 JSONB 문서입니다. 단일 매장·두 사용자라는 범위에서 전체 문서와 원장을 하나의 PostgreSQL 트랜잭션으로 커밋합니다. `revision`은 계산 조건의 변경을, DB `version`은 모든 저장 충돌을 감지합니다.

브라우저는 RLS로 자기 매장 데이터만 읽을 수 있고 직접 수정할 수 없습니다. Next.js 서버가 Supabase로 세션을 검증한 후 공통 명령 모듈을 적용하고, 서버 전용 RPC가 멤버십·버전·요청 UUID를 확인해 원자적으로 저장합니다. 외부 계정·익명 접근·RPC 직접 호출은 차단됩니다. 이미지 저장소는 비공개이며 매장 폴더별 권한과 5분짜리 서명 URL을 사용합니다.

MVP에는 기록 삭제 기능을 제공하지 않고 주문 취소·보정 기록을 남깁니다. 장기간 사용해 기록이 커지면 문서의 하위 컬렉션을 관계형 테이블로 분리할 수 있습니다. 매장 설정에서 JSON 백업을 내려받을 수 있습니다. 자동 복구·가져오기 UI는 포함하지 않습니다.

### 서버 인터페이스

| 경로                       | 용도                                                         |
| -------------------------- | ------------------------------------------------------------ |
| `GET /api/store`           | 로그인한 사용자의 매장 문서와 버전 조회                      |
| `POST /api/store`          | `{version, requestId, command}` 형태의 검증된 업무 명령 저장 |
| `POST /api/images`         | 참고 이미지 업로드                                           |
| `GET /api/images?path=...` | 해당 매장 이미지의 일시적 열람 URL                           |
| `POST /api/recommend`      | `{date, version}` 기준으로 검증된 추가 생산안 추천           |
| `POST /api/order-voice`    | 현재 사용 모드의 메뉴판과 주문 초안으로 Realtime WebRTC 연결 |

공유 모드의 API에는 `Authorization: Bearer <Supabase access token>`이 필요합니다. 음성 입력은 공유 모드가 아닐 때 로그인 없이도 연결할 수 있습니다. 중복 저장 요청은 같은 UUID로 재시도하면 중복 반영되지 않습니다. 충돌은 HTTP 409이며 새로 조회해 검토해야 합니다. 클라이언트는 실패 시 서버 상태를 성공한 것으로 가정하지 않습니다.

## Vercel 배포

Vercel에서 이 폴더를 Next.js 프로젝트로 가져오고 `.env.example`의 운영 값을 설정한 뒤 배포합니다. `NEXT_PUBLIC_` 값은 빌드에 포함되므로 바꾼 뒤 다시 빌드해야 합니다. `SUPABASE_SERVICE_ROLE_KEY`와 `OPENAI_API_KEY`에는 절대 `NEXT_PUBLIC_` 접두어를 붙이지 않습니다. 배포 주소를 Supabase의 인증 리디렉션 설정 및 `APP_URL`과 맞춥니다.

아이폰 Safari의 **홈 화면에 추가**, 안드로이드 Chrome의 **앱 설치/홈 화면에 추가**로 사용할 수 있습니다. 매니페스트·아이콘과 연결 실패 안내용 서비스 워커를 포함하며, 주문·인증·API 응답을 서비스 워커에 캐시하지 않습니다.

## 검증

```powershell
npm run typecheck
npm test
npm run build
```

도메인 테스트는 세트·박스 환산, 날짜별 생산 올림, 예약 여분, 기간별 부족, 생산 완료 중복 처리, 기준 변경 감지, 수령·마감 등을 확인합니다. DB 테스트는 실제 PostgreSQL 엔진(PGlite)에서 마이그레이션을 적용하고 RLS, 이미지 폴더 정책, 두 사용자 제한, 멱등성·버전 충돌을 검증합니다. 운영 Supabase 인증·메일·Storage와 OpenAI 호출, 실제 아이폰·안드로이드의 홈 화면 설치는 실제 서비스 설정 후 인수 테스트가 필요합니다.

## 후속 기능

### 스티커 그림 관리와 제작

PC에서는 사이드바의 **스티커**, 모바일에서는 **설정 → 스티커 그림 관리 · 제작**으로 엽니다.
PNG/JPG/WebP 그림을 등록하고 이름·여러 태그를 편집할 수 있습니다. 태그 필터는 선택한 태그를 모두 포함하는 그림을 보여줍니다. 보관한 그림은 필터의 `보관한 그림`에서 복원할 수 있습니다.

제작 화면에서 주문의 스티커 문구를 가져오거나 직접 입력합니다. 그림과 문구는 각각 드래그하거나 위치·영역 크기 슬라이더로 조절하고, 글꼴 계열·크기·굵기·색·정렬을 바꿉니다. 글꼴은 기기에서 사용 가능한 글꼴로 렌더링됩니다. 영역을 넘는 문구는 PNG 저장 전에 수정해야 합니다.

`stickerAssets`와 `stickerDesigns`는 기존 매장 문서의 선택 필드로 저장되어 이전 문서와 호환됩니다. 그림은 기존 비공개 이미지 저장소를 이용하고 서버에서 매장 소유권을 확인합니다. 체험 모드에서는 브라우저에만 저장됩니다. 디자인은 선택한 그림 경로를 보관하므로 원본 그림을 바꾸거나 보관해도 저장한 디자인의 그림은 유지됩니다. 이미지 파일을 직접 삭제하는 기능은 제공하지 않습니다.

PNG는 외부 확인용 단일 디자인 이미지입니다. 폼텍 3106·3639의 실제 크기 인쇄나 폼텍 편집 파일은 아직 지원하지 않습니다. 사용자에게 받을 폼텍 파일 예시로 규격과 편집 파일 구조를 확인한 뒤 구현합니다. 고객 대화·승인 상태 관리와 AI 이미지 생성은 포함하지 않습니다.

AI 스티커 제작, 판매 이력을 이용한 상시 메뉴 변경 추천, 비품 자동 발주, 쿠팡이츠 판매메뉴 자동 반영은 제외했습니다. 쿠팡이츠 연동은 **생산계획 → 별도로 수정 가능한 당일 판매목록 → 쿠팡이츠 반영**으로 확장하며, 해당 단계에서 지원 수단을 확인합니다.

## 메뉴판 갱신과 기존 데이터

기존 체험 데이터는 최초 로드 시 버전별로 업그레이드하여 메뉴판 36종을 등록합니다. 버전 1의 설기류·오븐떡은 재적용하지 않고, 버전 2에서 일반떡만 추가합니다. 같은 이름의 기존 메뉴는 ID와 레시피를 유지하고 사진·분류·박스 가격·포장 수량만 반영합니다. 이후 사용자가 수정한 메뉴는 다시 덮어쓰지 않습니다. 과거 주문은 저장 당시 박스 환산을 유지합니다. 공유 모드는 서버에서 동일한 업그레이드 문서를 조회하고 다음 업무 저장 시 DB에 함께 반영합니다.
